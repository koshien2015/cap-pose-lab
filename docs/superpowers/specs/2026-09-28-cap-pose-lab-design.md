# cap-pose-lab 設計

- 日付: 2026-09-28
- 状態: レビュー待ち
- 前提となる検証: 事前に作ったブラウザ実行ベンチ（非公開）での計測

## 1. 目的

キャップ野球の投球動画を、**ブラウザの中だけで**解析する公開サイトを作る。動画はサーバに送らない。

- 1本の動画から投手の骨格（キーポイント）を取り出し、フォームの数値を出す
- 2本の動画のフォームを棒人間で並べて・重ねて比較する（速度・加速度ベクトルを含む）
- キャップを検出し、投球の軌跡・コース・球速を推定する（試験的）

**非エンジニアでも迷わず使えること**を最優先にする。

### やらないこと（今回の範囲外）

- 解析結果のサーバ保存・v3 との連携（pose.json を書き出すところまで）
- 骨格を焼き込んだ動画の出力
- フォームの良し悪しの判定（`pitching/` の方針を引き継ぎ、観測値と差分だけを出す）
- リアルタイム（撮影しながら）の解析

## 2. 利用者と使う場面

- 選手・指導者が、スマホで撮った数秒の投球動画を、その場でスマホで解析する
- PC でも使えるが、**縦持ちのスマホを主な環境**とする

## 3. 設計の原則（非エンジニア向け）

1. 専門用語を画面に出さない。「WebGPU」ではなく「この端末は高速モードで解析できます」。技術的な詳細は「詳しい情報」に折りたたむ
2. 最初に撮影ガイドを見せる（投手の真横から全身、60fps 推奨、数秒で十分、良い例と悪い例の絵）
3. サンプル動画で一通りの流れを体験できる
4. 結果は数値に加えて言葉でも伝える（例:「2球目はリリースの瞬間、肘が1球目より約12°曲がっていました」）。良し悪しは判定しない
5. 指標には図入りの一行説明を付ける
6. エラーは「何が起きたか」と「次に何をすればよいか」をセットで出す
7. モデルは自動でダウンロードしない。サイズを見せて許可を取る
8. 解析中は残り時間を出す

## 4. 全体構成

- リポジトリ: `koshien2015/cap-pose-lab`（公開、AGPL-3.0）
- 公開先: GitHub Pages `https://koshien2015.github.io/cap-pose-lab/`
- 技術: Vite + React + TypeScript + Tailwind CSS、テストは Vitest と Playwright
- 推論: onnxruntime-web（WebGPU を優先し、使えない端末では wasm）
- 動画: mp4box.js で分離し、WebCodecs の VideoDecoder でデコードする

```
cap-pose-lab/
  src/
    inference/   環境判定・ORT セッション・動画デコード・レターボックス・YOLO 出力の解読
    tracking/    投手の特定と追跡（役割検出 → 無ければ最大の人物、タップで変更、bbox の重なりで追跡）
    analysis/    pitching/ の TS 移植（前処理・指標・イベント・同期・比較・ビューア用データ）
    capDetect/   動きによる区間の絞り込み・キャップ検出・NMS・軌跡フィット・ゾーン推定
    viewer/      棒人間ビューア（viewer_template の JS を React 化）
    ui/          画面（ステップ形式）
    content/     撮影ガイド・指標の説明・エラーメッセージの文言
  public/
    models/manifest.json   モデル一覧（ONNX 本体は CI で生成し、git には入れない）
    samples/               サンプル動画
  tools/
    export_models.py  ONNX 書き出し（ultralytics のバージョンを固定）
    make_fixtures.py  Python 版から数値一致テスト用の入力と期待値を書き出す
  .github/workflows/pages.yml
```

各ディレクトリは、他の層の中身を知らなくても使える関数・フックだけを公開する。`analysis/` と `capDetect/` の中核は、DOM にも ORT にも依存しない純粋関数にする（テストしやすくするため）。

## 5. モデルと配信

### 5.1 モデル一覧（manifest.json）

モデルの差し替えは、Release に重みを追加し、manifest を1行変えるだけで済むようにする。コードの変更は不要にする。

```json
{
  "pose": [
    { "id": "fast",     "label": "はやい",   "file": "yolo26n-pose.fp32.onnx", "imgsz": 960, "sizeMB": 12.5 },
    { "id": "standard", "label": "ふつう",   "file": "yolo26s-pose.fp32.onnx", "imgsz": 960, "sizeMB": 41 },
    { "id": "detailed", "label": "くわしい", "file": "yolo26m-pose.fp32.onnx", "imgsz": 960, "sizeMB": 84 }
  ],
  "capDetector": {
    "version": "20250510",
    "file": "cap-detector-20250510.fp16.onnx",
    "source": "https://github.com/koshien2015/cap-pose-lab/releases/tag/cap-detector-20250510",
    "imgsz": 640,
    "preprocess": "raw",
    "classes": ["cap", "pitcher_motion", "batter_stance", "umpire", "catcher", "pitcher_release",
                "batter_swing", "catcher_stance", "catcher_catch", "catcher_throw", "catcher_miss"],
    "output": "yolov8-raw",
    "license": "AGPL-3.0"
  }
}
```

- `preprocess`: `raw`（元フレーム）か `enhanced`（3フレーム差分によるモーション強調）。20250510 は元フレームで学習したので `raw`
- `output`: `yolo26-end2end`（NMS 不要）か `yolov8-raw`（`[1, 4+クラス数, anchors]`。NMS を JS で行う）

### 5.2 CI での書き出しと配信

- GitHub Actions が、公式の YOLO26 Pose の `.pt` と Release の検出モデル `.pt` をダウンロードし、`tools/export_models.py` で ONNX に書き出して、Pages の配信物に同梱する
- ultralytics のバージョンは固定する（検証時は 8.4.53）
- 姿勢推定は fp32 で配信する。検証（Mac Chrome）では fp16 が fp32 より約2倍遅かった
- キャップ検出は fp32 だと 104MB になり、1ファイル 100MB の制限を超えるので **fp16（約 52MB）** で配信する。fp32 が必要になったら、ONNX の外部データ形式で分割する
- ORT の wasm 本体（`ort-wasm-simd-threaded.jsep.{wasm,mjs}`、約 28MB）も同一オリジンから配信する。`env.wasm.wasmPaths` には **mjs と wasm の両方を明示する**（省略するとバンドル済みのチャンクがスレッド用 Worker に読み込まれ、止まる。検証で確認済み）

### 5.3 GitHub Pages の制約

- 独自のレスポンスヘッダ（COOP/COEP）を付けられないので、wasm は1スレッドで動く。WebGPU を主に使い、wasm は WebGPU の無い端末向けに「はやい」モードだけを選べるようにする
- ベースパスは `/cap-pose-lab/`

## 6. 画面の流れ

縦持ち前提の1カラムで、上から順に進むステップ形式にする。

| # | 画面 | 内容 |
|---|---|---|
| 0 | はじめに | 撮影ガイド、サンプル動画で試すボタン |
| 1 | 環境チェック | ◎ / △ / × と一言。詳細は折りたたみ |
| 2 | 動画を選ぶ | 1本（解析）か2本（比較）。サムネイル・長さ・fps |
| 3 | 解析モード | 軽い順に「はやい / ふつう / くわしい」。各カードにダウンロードサイズ・この動画での推定時間・精度の目安。端末でのおすすめに印。「キャップ検出もする（試験的）」のチェック |
| 4 | ダウンロード確認 | 取得するファイルと合計サイズ。キャッシュ済みのものは除く |
| 5 | 解析中 | 動画ごとの進捗・残り時間・キャンセル。Wake Lock で画面を消さない。「アプリを切り替えると止まります」の案内 |
| 6 | 投手の確認 | 自動で選んだ投手を枠で表示。違えばタップで選び直す |
| 7 | イベント指定 | コマ送り（大きなスライダーと ±1 フレームのボタン）で「足接地」「リリース」を指定。投げ腕と打者の向きを切り替える |
| 8 | ビューア | 下記 |
| 9 | 書き出し | 動画ごとに pose.json・metrics.json、キャップ検出をしたら軌跡 JSON |

### 6.1 解析モードの目安（検証値、Mac Chrome・WebGPU・4.5秒 149フレーム）

| モード | 1フレーム | 通し時間 | m@960 との肘角度の差（平均） |
|---|---|---|---|
| はやい（n@960） | 23 ms | 5.2 秒 | 約 5° |
| ふつう（s@960） | 40 ms | 7.7 秒 | 約 4° |
| くわしい（m@960） | 85 ms | 14.7 秒 | 基準 |

推定時間は、最初は端末の種類から目安を出し、一度解析したら実測の速度（端末に保存）で出し直す。

### 6.2 ビューア

`pitching/visualization/viewer_template.py` の機能をすべて引き継ぐ。

- 表示: 並べて / 重ねて
- そろえ方: 進行率 0〜100%（足接地〜リリース）/ リリース基準 / フレーム番号
- 再生・コマ送り、投球腕の軌跡
- 速度・加速度ベクトル（対象: 全関節 / 投球腕 / 単一関節、矢印の長さの上限と頭打ちの表示）
- その時点の肘角度・前腕角度・体幹の傾き・前脚の膝角度と、2球の差
- スマホ: 再生の操作は画面下に固定。指標はカードで折りたたむ。横向きにすると2画面を横に並べる
- キャップ検出をした場合は、軌跡・コース・球速を「推定値（試験的）」と明記して表示する

### 6.3 スマホ向けの共通ルール

- タップ領域は 44px 以上。ホバーに頼らない
- safe area の余白を取る
- 同意・エラーは画面内のパネルで出す（`alert` / `confirm` は使わない）
- 対象は iOS Safari と Android Chrome の最新2バージョン

## 7. 推論の詳細

事前検証で作ったベンチの実装を移植する。

- 前処理: 長辺を imgsz に合わせ、短辺を32の倍数までパディング（値114、中央寄せ）。Python 版の `.pt` 推論と完全に一致することを確認済み（fp32 で 0.00px）
- デコード: 1フレームずつ取り出して処理し、全フレームをメモリに溜めない。回転メタデータ（iPhone の縦動画）を反映する
- セッションは処理が終わるたびに解放する
- 姿勢推定の出力（`[1, 300, 57]`）は NMS 不要。信頼度 0.25 以上を人物とする

### 7.1 投手の特定

1. キャップ検出をオンにした場合: 役割の検出（pitcher_motion / pitcher_release）の bbox と骨格を突き合わせる（`shared/pose.py` と同じ考え方）
2. オフの場合: 最初のフレームで最も大きい人物を投手とする
3. どちらの場合も、画面 6 でタップして選び直せる。以降は bbox の重なり（IoU）で追う

## 8. 解析ロジックの移植（`pitching/` → TS）

- 対象: 信頼度フィルタ・補間・平滑化・指標・イベント・同期（進行率 / イベント基準）・比較・ビューア用データ（`build_payload`）。約2,000行
- `scipy.signal.savgol_filter` は、係数の計算を含めて TS で実装する
- 入力の JSON 形式は `pose_export.py` と同じ `SCHEMA_VERSION 1`。書き出した pose.json は Python 版（`python -m pitching run --pose ...`）でもそのまま読める
- リリースはポーズだけで断定しない（`events/detector.py` の方針）。手動指定を基本とし、キャップ検出がある場合は「手首とキャップが離れた最初のフレーム」を候補として示す

### 8.1 Python 版との数値一致

- `tools/make_fixtures.py` が Python 版を実行して、入力と期待値を `src/**/__fixtures__/*.json` に書き出す
- TS 側のテストで、同じ入力から同じ値（許容誤差内）が出ることを確かめる
- 移植元のテスト（`pitching/tests` の206件、`shared/tests/test_trajectory_fitter.py` の27件）のうち、ロジック部分は TS 側にも対応するテストを作る

## 9. キャップ検出（試験的）

1. 動きによる区間の絞り込み: 3フレーム差分の活動量から投球の区間を出す（`prefilter.py` を移植）
2. 検出: 区間内のフレームを manifest の前処理（今回は元フレーム）と入力サイズで推論する。出力 `[1, 15, anchors]` を解読し、クラスごとに NMS をかける
3. 軌跡: 時間の2次式を RANSAC でフィットし、誤検出の除去・欠損の補間・9分割のコース・平均球速を出す（`trajectory_fitter.py` を移植。信頼度は 0.15 と低めにし、誤検出は軌跡フィットで除く）
4. ゾーン: 打者と捕手の bbox からストライクゾーンを推定し、座標を正規化する（`pitching_analysis.py` のロジック部分を移植）
5. 表示には必ず「推定値（試験的）」と付ける。単眼カメラなので横変化の真値や瞬間の球速は出せないことを説明に書く

## 10. エラー処理

| 状況 | 画面の案内 |
|---|---|
| 動画を読めない・対応していないコーデック | 何が起きたかと、撮影設定の変え方（例: iPhone の「設定 > カメラ > フォーマット > 互換性優先」） |
| 高速モードに対応していない | 「はやい」モードだけを選べる理由を説明する |
| メモリ不足・タブが落ちた | 再読み込み後に、終わった動画の結果から再開する（結果は動画ごとに IndexedDB に保存） |
| ダウンロード失敗 | 再試行のボタン。モバイル回線の場合は Wi-Fi をすすめる |
| 投手が見つからない | 投手をタップで選ぶよう案内する |

技術的な詳細（例外メッセージ・環境情報）は「詳しい情報」に折りたたみ、コピーできるようにする（問い合わせ用）。

## 11. テスト

- ユニットテスト: 前処理・出力の解読・NMS・追跡・移植ロジック・軌跡フィット。数値一致テストを含め、カバレッジ 80% 以上
- E2E（Playwright）: サンプル動画で「動画選択 → 解析 → イベント指定 → ビューア → 書き出し」を通す。CI では wasm と「はやい」モードで実行する
- 実機確認: iPhone Safari・Android Chrome での確認手順を README に書く（CI では自動化できないため）

## 12. 未確認事項とリスク

- **iPhone Safari は未計測**（WebGPU の速度、HEVC・縦動画・60fps のデコード、メモリ）。実装の早い段階で、実機で検証ページ相当の計測をする
- WebGPU で1フレームあたり約 20ms の固定費がある（n で 640 と 960 の差がほぼない）。結果の読み戻しか、CPU に回るノードが原因とみられる。速くする余地として後で調べる
- キャップ検出モデルは入力 640 で学習している。manifest は学習時と同じ 640 で始め、960 で推論したときの検出率と比べて見直す（キャップは画面上で小さいため、960 のほうが拾える可能性がある）
- GitHub Pages の転送量の目安（月 100GB）。キャッシュを効かせ、「くわしい」モードは必要な人だけが選ぶ設計で抑える
- ライセンス: Ultralytics の重み（AGPL-3.0）をブラウザに配るため、リポジトリ全体を AGPL-3.0 で公開する
