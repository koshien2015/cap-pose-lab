# cap-pose-lab 設計

- 日付: 2026-09-28
- 状態: 計画1・2・5 実装済み。§9 キャップ検出を 2026-09-29 に改訂（計画5 の前提）。§14 打者モードを 2026-09-29 に追加（計画6 の前提）
- 前提となる検証: 事前に作ったブラウザ実行ベンチ（非公開）での計測

## 1. 目的

キャップ野球の投球動画を、**ブラウザの中だけで**解析する公開サイトを作る。動画はサーバに送らない。

- 1本の動画から投手の骨格（キーポイント）を取り出し、フォームの数値を出す
- 2本の動画のフォームを棒人間で並べて・重ねて比較する（速度・加速度ベクトルを含む）
- 投手の後方から撮った1球分の動画でキャップを検出し、投球の軌跡と平均球速を推定する（試験的。フォーム比較とは別の機能）
- 捕手の後方から撮った打者のスイングを、同じ仕組みで2本比べる（§14）

**非エンジニアでも迷わず使えること**を最優先にする。

### やらないこと（今回の範囲外）

- 解析結果のサーバ保存・v3 との連携（pose.json を書き出すところまで）
- 骨格を焼き込んだ動画の出力
- フォームの良し悪しの判定（`pitching/` の方針を引き継ぎ、観測値と差分だけを出す）
- リアルタイム（撮影しながら）の解析
- ストライクゾーンの推定と9分割のコース判定（2026-09-29 に範囲外とした。§9）

## 2. 利用者と使う場面

- 選手・指導者が、スマホで撮った数秒の投球動画を、その場でスマホで解析する
- PC でも使えるが、**縦持ちのスマホを主な環境**とする
- 投球の軌跡は、試合を投手の後方から撮った映像を1球ずつ切り出して使う（フォーム比較の「投手の真横から」とは撮る向きが違う）

## 3. 設計の原則（非エンジニア向け）

1. 専門用語を画面に出さない。「WebGPU」ではなく「この端末は高速モードで解析できます」。技術的な詳細は「詳しい情報」に折りたたむ
2. 最初に撮影ガイドを見せる（投手の真横から全身、60fps 推奨、数秒で十分、良い例と悪い例の絵）
3. サンプル動画で一通りの流れを体験できる
4. 結果は数値に加えて言葉でも伝える（例:「2球目はリリースの瞬間、肘が1球目より約12°曲がっていました」）。良し悪しは判定しない
5. 指標には図入りの一行説明を付ける
6. エラーは「何が起きたか」と「次に何をすればよいか」をセットで出す
7. モデルは自動でダウンロードしない。サイズを見せて許可を取る
8. 解析中は残り時間を出す

## 4. 全体構成

- リポジトリ: `koshien2015/cap-pose-lab`（公開、AGPL-3.0）
- 公開先: GitHub Pages `https://koshien2015.github.io/cap-pose-lab/`
- 技術: Vite + React + TypeScript + Tailwind CSS、テストは Vitest と Playwright
- 推論: onnxruntime-web（WebGPU を優先し、使えない端末では wasm）
- 動画: mp4box.js で分離し、WebCodecs の VideoDecoder でデコードする

```
cap-pose-lab/
  src/
    inference/   環境判定・ORT セッション・動画デコード・レターボックス・YOLO 出力の解読
    tracking/    投手の特定と追跡（最初のフレームで最大の人物、タップで変更、bbox の重なりで追跡）
    analysis/    pitching/ の TS 移植（前処理・指標・イベント・同期・比較・ビューア用データ）
    capDetect/   検出出力の解読と NMS・推論の間引き・差分強調・リリース候補・軌跡フィットと球速（§9）
    trajectory/  投球の軌跡の画面（§9）
    viewer/      棒人間ビューア（viewer_template の JS を React 化）
    ui/          画面（ステップ形式）
    content/     撮影ガイド・指標の説明・エラーメッセージの文言
  public/
    models/manifest.json   モデル一覧（ONNX 本体は CI で生成し、git には入れない）
    samples/               サンプル動画
  tools/
    export_models.py  ONNX 書き出し（ultralytics のバージョンを固定）
    make_fixtures.py  Python 版から数値一致テスト用の入力と期待値を書き出す
  .github/workflows/pages.yml
```

各ディレクトリは、他の層の中身を知らなくても使える関数・フックだけを公開する。`analysis/` と `capDetect/` の中核は、DOM にも ORT にも依存しない純粋関数にする（テストしやすくするため）。

## 5. モデルと配信

### 5.1 モデル一覧（manifest.json）

モデルの差し替えは、Release に重みを追加し、manifest を1行変えるだけで済むようにする。コードの変更は不要にする。

```json
{
  "pose": [
    { "id": "fast",     "label": "はやい",   "file": "yolo26n-pose.fp32.onnx", "imgsz": 960, "sizeMB": 12.5 },
    { "id": "standard", "label": "ふつう",   "file": "yolo26s-pose.fp32.onnx", "imgsz": 960, "sizeMB": 41 },
    { "id": "detailed", "label": "くわしい", "file": "yolo26m-pose.fp32.onnx", "imgsz": 960, "sizeMB": 84 }
  ],
  "capDetector": {
    "version": "y26m-1280",
    "weights": "yolo26m-1280px-120epoch.pt",
    "sha256": "f6d5f8dc339f9396b6107a5e6d1b420f521227b101df29bd887a09e92baed87f",
    "file": "cap-detector-y26m-1280.fp32.onnx",
    "source": "https://github.com/koshien2015/cap-pose-lab/releases/tag/cap-detector-y26m-1280",
    "imgsz": 1280,
    "sizeMB": 84.3,
    "precision": "fp32",
    "preprocess": "enhanced",
    "classes": ["cap", "pitcher_motion", "batter_stance", "umpire", "catcher", "pitcher_release",
                "batter_swing", "catcher_stance", "catcher_catch", "catcher_throw", "catcher_miss"],
    "output": "yolo26-end2end",
    "license": "AGPL-3.0"
  }
}
```

- `weights` と `sha256`: `tools/export_models.py` は `source` の Release から重みを取得し、ハッシュが一致しなければ止まる

- `preprocess`: `raw`（元フレーム）か `enhanced`（3フレーム差分によるモーション強調）。今のモデル（YOLO26m-P2・入力 1280）は元フレームで学習したが、Python 版の推論（`track.py`）と同じく `enhanced` で推論する（2026-09-29 ユーザー判断。手元の動画で、止まったキャップを拾わず飛んでいる間だけを連続で検出した）
- `precision`: `fp32` か `fp16`。fp16 は書き出し後に変換する（入出力は float32 のまま）
- `output`: `yolo26-end2end`（NMS 不要）か `yolov8-raw`（`[1, 4+クラス数, anchors]`。NMS を JS で行う）

### 5.2 CI での書き出しと配信

- GitHub Actions が、公式の YOLO26 Pose の `.pt` と Release の検出モデル `.pt` をダウンロードし、`tools/export_models.py` で ONNX に書き出して、Pages の配信物に同梱する
- ultralytics のバージョンは固定する（検証時は 8.4.53）
- 姿勢推定は fp32 で配信する。検証（Mac Chrome）では fp16 が fp32 より約2倍遅かった
- キャップ検出（YOLO26m-P2・入力 1280）は fp32 で 84MB なので、そのまま配信する。1ファイルが 100MB を超えるモデルに替えるときは `precision: "fp16"` にする（2026-09-29 の計測では、旧モデル YOLOv8m@640 で fp16 は fp32 の約1.8倍遅かった）
- ORT の wasm 本体（`ort-wasm-simd-threaded.jsep.{wasm,mjs}`、約 28MB）も同一オリジンから配信する。`env.wasm.wasmPaths` には **mjs と wasm の両方を明示する**（省略するとバンドル済みのチャンクがスレッド用 Worker に読み込まれ、止まる。検証で確認済み）

### 5.3 GitHub Pages の制約

- 独自のレスポンスヘッダ（COOP/COEP）を付けられないので、wasm は1スレッドで動く。WebGPU を主に使い、wasm は WebGPU の無い端末向けに「はやい」モードだけを選べるようにする
- ベースパスは `/cap-pose-lab/`

### 6.1 解析モードの目安（検証値、Mac Chrome・WebGPU・4.5秒 149フレーム）

| モード | 1フレーム | 通し時間 | m@960 との肘角度の差（平均） |
|---|---|---|---|
| はやい（n@960） | 23 ms | 5.2 秒 | 約 5° |
| ふつう（s@960） | 40 ms | 7.7 秒 | 約 4° |
| くわしい（m@960） | 85 ms | 14.7 秒 | 基準 |

推定時間は、最初は端末の種類から目安を出し、一度解析したら実測の速度（端末に保存）で出し直す。

### 6.2 ビューア

`pitching/visualization/viewer_template.py` の機能をすべて引き継ぐ。

- 表示: 並べて / 重ねて
- そろえ方: 進行率 0〜100%（足接地〜リリース）/ リリース基準 / フレーム番号
- 再生・コマ送り、投球腕の軌跡
- 速度・加速度ベクトル（対象: 全関節 / 投球腕 / 単一関節、矢印の長さの上限と頭打ちの表示）
- その時点の肘角度・前腕角度・体幹の傾き・前脚の膝角度と、2球の差
- スマホ: 再生の操作は画面下に固定。指標はカードで折りたたむ。横向きにすると2画面を横に並べる

### 6.3 スマホ向けの共通ルール

- タップ領域は 44px 以上。ホバーに頼らない
- safe area の余白を取る
- 同意・エラーは画面内のパネルで出す（`alert` / `confirm` は使わない）
- 対象は iOS Safari と Android Chrome の最新2バージョン

## 7. 推論の詳細

事前検証で作ったベンチの実装を移植する。

- 前処理: 長辺を imgsz に合わせ、短辺を32の倍数までパディング（値114、中央寄せ）。Python 版の `.pt` 推論と完全に一致することを確認済み（fp32 で 0.00px）
- デコード: 1フレームずつ取り出して処理し、全フレームをメモリに溜めない。回転メタデータ（iPhone の縦動画）を反映する
- セッションは処理が終わるたびに解放する
- 姿勢推定の出力（`[1, 300, 57]`）は NMS 不要。信頼度 0.25 以上を人物とする

### 7.1 投手の特定

1. 最初のフレームで最も大きい人物を投手とする
2. 画面 6 でタップして選び直せる。以降は bbox の重なり（IoU）で追う

キャップ検出の役割クラスで投手を選ぶ案（`shared/pose.py` の考え方）は採らない。キャップ検出は撮る向きが違う別の機能にしたため（§9）。

## 8. 解析ロジックの移植（`pitching/` → TS）

- 対象: 信頼度フィルタ・補間・平滑化・指標・イベント・同期（進行率 / イベント基準）・比較・ビューア用データ（`build_payload`）。約2,000行
- `scipy.signal.savgol_filter` は、係数の計算を含めて TS で実装する
- 入力の JSON 形式は `pose_export.py` と同じ `SCHEMA_VERSION 1`。書き出した pose.json は Python 版（`python -m pitching run --pose ...`）でもそのまま読める
- リリースはポーズだけで断定しない（`events/detector.py` の方針）。手動指定とする

### 8.1 Python 版との数値一致

- `tools/make_fixtures.py` が Python 版を実行して、入力と期待値を `src/**/__fixtures__/*.json` に書き出す
- TS 側のテストで、同じ入力から同じ値（許容誤差内）が出ることを確かめる
- 移植元のテスト（`pitching/tests` の206件、`shared/tests/test_trajectory_fitter.py` の27件）のうち、ロジック部分は TS 側にも対応するテストを作る
- 意図的に Python 版と変えた点: ビューアの「進行率」でコマを並べ直すとき、補間しない長さの欠損（4コマ以上）をまたいで直線でつながない（観測していない動きを描かないため）。Python 版は同じ場面で直線補間する

## 9. キャップ検出と投球の軌跡（試験的）

2026-09-29 に範囲を見直した。フォーム比較（投手の真横から撮る）とは撮る向きが違うため、**別の機能**として作る。ストライクゾーンの推定と9分割のコース判定はやらない。

### 9.1 目的と入力

- 入力: 試合を**投手の後方から**撮った映像を、1球ずつ切り出した動画1本。上限はフォーム比較と同じ（20秒・1200コマ・200MB）
- 出すもの: キャップの軌跡（映像に重ねて描く）と平均球速。どちらも「推定値（試験的）」と明記する
- 単眼カメラなので、横変化の真値や瞬間の球速は出せないことを説明に書く

### 9.2 構成

`src/capDetect/` は DOM にも ORT にも依存しない純粋関数にする。

| ファイル | 役割 | 移植元 |
|---|---|---|
| `decodeDetect.ts` | 出力を解読し、信頼度が 0.15 より大きいものを元の動画の座標に戻す。`yolo26-end2end`（`[1, 300, 6]`）はそのまま、`yolov8-raw`（`[1, 4+クラス数, anchors]`）はクラスごとに NMS にかける | ultralytics の後処理 |
| `gate.ts` | 推論の間引き。キャップが見つかるまで5コマに1回推論し、見つけたら30コマ連続で推論する。見つけたときは、直前の推論していないコマ（最大4コマ）を遡って推論させる | `prefilter.py` の `InferenceGate` に遡りを追加 |
| `enhance.ts` | 3コマ差分によるモーション強調（manifest の `preprocess` が `enhanced` のとき） | `tennis.py` |
| `release.ts` | 投手のクラスが `pitcher_motion` から `pitcher_release` に切り替わったコマをリリース候補にする | `pitching_analysis.py` の `detect_release` |
| `trajectory.ts` | 時間の2次式フィット・RANSAC・欠損の補間・平均球速 | `trajectory_fitter.py` |

- 推論のループは `src/inference/runDetect.ts`。`runPose` と同じく1コマずつデコードして閉じる。遡って推論するため、直近4コマの入力だけを手元に残す。`enhanced` のときは次のコマを1枚待って差分をとる
- 1コマにキャップが複数あれば、信頼度が最も高いものを採る（Python 版と同じ）
- 投球区間の自動検出（`prefilter.py` の `scan_activity`）は移植しない。切り出した動画では区間が立たないため（`PIPELINE.md` の記録どおり）
- 画面は `src/trajectory/` にまとめ、`App.tsx` はスタート画面から分岐させるだけにする

### 9.3 画面の流れ

| # | 画面 | 内容 |
|---|---|---|
| 0 | はじめに | 「投球の軌跡を見る（試験的）」。下に「投手の後ろから撮った、1球分の動画」と添える |
| 1 | 環境チェック | フォーム比較と同じ。検出モデルは1つなのでモードは選ばせない。WebGPU の無い端末でも動かすが、推定時間を見せてから進ませる |
| 2 | 動画を選ぶ | 1本 |
| 3 | ダウンロード確認 | 検出モデルのサイズ（キャッシュ済みなら省く） |
| 4 | 解析中 | 進捗はデコードしたコマ数、残り時間はそれまでの処理速度から出す。Wake Lock で画面を消さない |
| 5 | 結果 | 下記 |

結果画面:

- 最後にキャップが写っていたコマの画像に、フィットした軌跡の線と、検出した点を重ねる。検出した点は誤検出かどうかで分けず、すべて同じ印で描き、「詳しい情報」に全点（コマ・位置・信頼度）を並べる
- コマ送り（大きなスライダーと ±1 コマのボタン）で、そのコマの検出位置を見られる
- リリース: 自動の候補を表示し、「このコマをリリースにする」で直せる。直すとその場でフィットし直す。リリースより前の検出は使わない
- 結果カード: 「平均球速 約 ◯◯ km/h（推定値・試験的）」と一行の説明（リリースから最後にキャップが見えたコマまでの時間で、投本間 9.22m を割った平均）。検出したコマ数・推論したコマ数・推論時間は「詳しい情報」に折りたたむ
- 書き出し: `{動画名}_trajectory.json`
- コマの画像は縮小画像の仕組みを使い、連続で推論した区間（キャップが飛んでいる間）は全コマを残す
- 保存した JSON をもう一度読み込む機能は作らない

### 9.4 データの流れ

1. デコード →（`enhanced` なら差分強調）→ `gate` が推論するか決める → 推論 → `decodeDetect`
2. コマごとに、キャップの位置と信頼度（無ければ null）・投手の状態・推論したかどうかを記録する。推論していないコマは「推論していない」として区別する（「推論して見つからなかった」と混ぜると、欠損の扱いを誤るため）
3. ループの後に `release.ts` でリリース候補を出し、`trajectory.ts` でフィット・補間・球速を計算する
4. リリースが見つからず、指定もされない場合は、最初の検出を t=0 とする。球速は採用した点の時間幅だけで決まるので変わらない

### 9.5 書き出す JSON

座標は回転を反映した後の画面ピクセル、`t` はリリースからの秒数。

```jsonc
{
  "schema": "cap-pose-lab/trajectory", "version": 1,
  "video": { "file": "…", "fps": 59.94, "width": 1080, "height": 1920, "frameCount": 420 },
  "model": { "weights": "yolo26m-1280px-120epoch.pt", "imgsz": 1280, "preprocess": "raw", "conf": 0.15 },
  "release": { "frame": 123, "source": "auto" },          // source: auto | manual | none
  "detections": [{ "frame": 125, "x": 540.2, "y": 812.7, "conf": 0.42 }],
  "inferredFrames": [[0, 1], [5, 6], [120, 156]],         // 推論したコマの範囲（end は含まない）
  "fit": { "coeffsX": [0, 0, 0], "coeffsY": [0, 0, 0], "rmse": 3.1,
           "inlierFrames": [125, 126], "outlierFrames": [131] },   // フィットできなければ null
  "trajectory": [{ "frame": 125, "t": 0.033, "x": 540.2, "y": 812.7, "interpolated": false }],
  "speedKmh": 72.4                                         // 出せなければ null
}
```

### 9.6 失敗したときの案内

| 状況 | 画面の案内 |
|---|---|
| 軌跡に乗る点が5点未満（検出ゼロを含む） | 「キャップの軌跡を見つけられませんでした」。撮り方の見直し（投手の後ろから、キャップが飛ぶ範囲まで画面に入れる／明るい場所で撮る／1080p・60fps 以上）をすすめる。検出できた点があれば画像に重ねて見せる |
| リリース候補が見つからない | エラーにしない。「リリースのコマが見つかりませんでした。コマ送りで指定できます」 |
| 指定したリリースより後の検出が足りない | 上の「見つけられませんでした」に「リリースより後にキャップが見えているコマが足りません」を添える |
| 球速が 30〜150 km/h から外れる | 値は出したうえで「途中で見失った可能性があります」と注記する |
| GPU が使えない・ダウンロード失敗・動画を読めない | フォーム比較と同じ仕組み（CPU への切り替え・再試行・`errors.ts` の文言）を使う |

### 9.7 Python 版と意図的に変える点

1. ゾーン・コース・カメラ角度の補正はなくす（`pitching_analysis.py` のゾーンは幅が 150px 固定で、動画の解像度が変わると壊れる。今回は範囲外とした）
2. RANSAC は画面のピクセル座標で判定する。外れ値の閾値は画面の高さの 1.5%（1080p で約16px）を仮の値とし、実際の映像での確認（§9.8）で調整する。Python 版は正規化座標で 0.15
3. RANSAC の乱数はシード付きの自前実装にする。点の並びが紛らわしい場合は、採用する点の組み合わせが Python 版と変わりうる
4. 投球区間の自動検出は移植せず、遡って推論する仕組みを足す（投げ始めを取りこぼすと時間幅が短くなり、球速が高く出るため）
5. リリース候補は間引いて推論したコマから決めるため、数コマずれることがある。手で直せるので許容する
6. 差分強調（`enhanced`）は、縮小（レターボックス）した後の画素で行う。Python 版は元の解像度で強調してから縮小する。余白は強調せず 114 のままにする
7. キャップの中心は小数のまま持つ。Python 版は画素を整数に切り捨てる（1px 未満の差）

### 9.8 テスト

- 数値一致（§8.1 と同じ方法）: 2次式のフィット・欠損の補間・球速・差分強調。fixture は `tools/make_fixtures.py` を拡張し、合成データから作る（実在の映像は使わない）
- RANSAC は数値一致の対象にせず、挙動をテストする（放物線に3割の外れ値を混ぜると外れ値を除いて係数が真値に近づく、5点未満や全点同時刻で例外になる）。移植元の27件のうち、ゾーン以外のケースを TS にも作る
- NMS と出力の解読: Python で合成した出力テンソルに ultralytics の `non_max_suppression` をかけた結果を期待値にする。レターボックスから元の座標への戻しも確かめる
- `gate`・`release` のユニットテスト（遡って推論する動き・推論しなかったコマの扱いを含む）
- 結果画面のテスト（失敗時の案内、リリースを直すとフィットし直す）
- 実際の映像での確認（手作業）: 手元の1本を Python の `track.py`（同じ重み・640・前段の絞り込みなし）とブラウザ版で処理し、検出数と球速がおおむね合うことを確かめる。手順は README に書く
- E2E は計画4で扱う

## 12. 未確認事項とリスク

- **iPhone Safari は未計測**（WebGPU の速度、HEVC・縦動画・60fps のデコード、メモリ）。実装の早い段階で、実機で検証ページ相当の計測をする

- キャップ検出モデルは入力 640 で学習している。manifest は学習時と同じ 640 で始め、960 で推論したときの検出率と比べて見直す（キャップは画面上で小さいため、960 のほうが拾える可能性がある）
- キャップ検出（入力 1280・fp32）は Mac Chrome で1回 146ms（WebGPU）・4.6秒（wasm）。wasm の端末では 20秒の動画で約20分かかる。iPhone は未計測
- RANSAC の閾値（画面の高さの 1.5%）は仮の値。実際の映像での確認で見直す
- GitHub Pages の転送量の目安（月 100GB）。キャッシュを効かせ、「くわしい」モードは必要な人だけが選ぶ設計で抑える
- ライセンス: Ultralytics の重み（AGPL-3.0）をブラウザに配るため、リポジトリ全体を AGPL-3.0 で公開する

## 14. 打者モード（計画6）

2026-09-29 に追加。投手のフォーム比較と同じ仕組み（骨格の取り出し・追跡・平滑化・比較画面）で、打者のスイングを2本比べる。

### 14.1 目的と入力

- 選手が自分のスイングを見比べる。良し悪しは判定しない（§1 の方針のまま）
- 動画は**捕手の後方（背面）**から撮る。試合映像を想定し、奥に投手、打者の横に主審・捕手が写る
- 動画の長さの上限はフォーム比較と共通（`src/inference/videoLimits.ts`）
- **動画の先頭を構えとみなす**。構えから撮り始めるよう画面で案内する

### 14.2 基準の瞬間

打者の足の接地は、すり足やノーステップがあって決められない。そのため、足接地は基準にしない。

| 瞬間 | 指定 | 使いみち |
|---|---|---|
| インパクト | 手動・任意（推奨） | 2本を揃える基準。空振りは「当たるはずだったコマ」 |
| トップ（手が一番捕手側に来た瞬間） | 手動・任意 | トップ=0% → インパクト=100% の進行率 |

- 骨格の動きだけでは決めない（§8 のリリースと同じ方針）
- トップはインパクトより前でなければならない
- インパクトが未指定なら「コマ番号で合わせる」のみ。トップも指定すれば「進行率で合わせる」も使える
- どれも未指定でも、ずらしスライダー（§14.6）で手合わせして比べられる
- 打ち方（右打ち／左打ち）は必須。初期値は右打ち

### 14.3 構成

投手の解析（`src/analysis/analyzePitch.ts` ほか）は変えない。打者の解析は別のモジュールにし、次のものを共通で使う。

- 前処理: 信頼度フィルタ・短い欠損の補間・平滑化（`preprocess.ts`・`savgol.ts`）
- キーポイントの読み込み: `tracks.ts`
- 追跡: `tracking/pitcherTracking.ts`（中身は「1人を追う」だけなので、そのまま使う）

比較画面（`src/viewer/`）は、投手・打者に共通の1つにする。投手に固有の書き込み（足接地・リリース・投球腕）を、比較用のデータ（`ViewerPayload`）の側に移す。

- `subject`: `'pitcher' | 'batter'`
- `anchor_event`: 揃える基準の瞬間の名前（投手 `release`、打者 `impact`）
- `event_labels`: 目盛りに出す瞬間とその表示名（投手は今の4つ、打者は `top`・`impact`）
- 各投球（各スイング）の `arm_joints` と `arm_label`: 対象の選択肢「投球腕」／「両手」が指す関節
- 各投球（各スイング）の `trail_joints`: 軌跡を描く関節（投手は投球腕の手首と肘、打者は `hands`）
- 各投球（各スイング）の `summary`: まとめの値（投手は空）
- 各投球（各スイング）の `scale_mode`: 投手 `shoulder_width`、打者 `torso_length`
- `reading_notes`: 「読み方」の文

揃え方の `release` は `anchor` に改め、表示名は `anchor_event` から作る（投手は「リリースに合わせる」、打者は「インパクトに合わせる」）。

### 14.4 座標の揃え方

- **大きさ**: 胴の長さ（肩の中点〜腰の中点の距離の、全コマでの中央値、画素）を 1 とする。打者は回転で見かけの肩幅が大きく変わるため、投手の「両肩の幅」は使えない
- **原点**: 構え（先頭）で腰の中点。先頭で腰が写っていなければ、腰が写っている最初のコマを使う
- **向き**: Y は上が正。X は**ホームベース側が正**。背面からだと、右打者はホームベースが画面の右、左打者は左に来るので、左打者は左右を反転する。これで右打者と左打者を並べても向きが揃う
- 前の側（前肩・前腰・前足）は、右打者なら左、左打者なら右

### 14.5 計算する値

座標はすべて §14.4 で揃えたもの（胴の長さ＝1）。

**グラフ（コマごと）**

| キー | 表示名 | 計算 |
|---|---|---|
| `shoulder_open` | 肩の開き | 後ろ肩の X − 前肩の X |
| `hip_open` | 腰の開き | 後ろ腰の X − 前腰の X |
| `head_x` | 頭の左右 | 頭の X − 構えでの頭の X |
| `head_y` | 頭の上下 | 頭の Y − 構えでの頭の Y |
| `hands_x` | 手の左右 | 両手首の中点の X |
| `hands_y` | 手の高さ | 両手首の中点の Y |

- 開きは、構えで 0 付近（両肩が奥行き方向に重なる）、投手側を向くほど大きくなる。**写った幅から見た値で、角度ではない**
- 頭は両耳の中点を使う。背面からだと鼻・目は写りにくいため。片耳でも欠けたコマは値を空ける
- 「構えでの頭」は、先頭から見て頭が取れた最初のコマ
- 両手首の中点は `hands` という点として比較用のデータに足し、骨格と一緒に描けるようにする（関節の選択肢の名前は「両手」）

**まとめ（1本につき1つ）**

| キー | 表示名 | 計算 | 出せないとき |
|---|---|---|---|
| `open_lag_ms` | 開きの時間差 | 腰の開く速さが最大のコマから、肩の開く速さが最大のコマまでの時間（ms）。＋は腰が先 | 探す範囲に値が3コマ未満 |
| `head_max_move` | 頭の最大移動 | 構え〜インパクトで、頭が構えの位置から一番離れた距離 | インパクト未指定 |
| `stride_dir` | 踏み込みの向き | 前足首の X の移動（構え → インパクト）。+0.1 より大きければ「閉じ（踏み込み）」、−0.1 より小さければ「開き（アウトステップ）」、それ以外は「ほぼまっすぐ」 | インパクト未指定、または前足首が取れない |

- 開く速さは、開きの値の中央差分（隣り合うコマの差 × fps）
- 時間差を探す範囲は、トップ（未指定なら先頭）からインパクト（未指定なら最後）
- 出せない値は「—」にし、理由を添える（例: 「インパクトを指定すると出ます」）
- 投手方向（奥行き）の動きは測れないことを「読み方」に書く

### 14.6 比較画面

- **ずらしスライダー（投手・打者共通）**
  - 2本を比べるときだけ「2本目をずらす」を出す。−1／＋1 のボタン、スライダー、0 に戻すボタンを並べる
  - 範囲は ± 長いほうの動画のコマ数。＋n なら、同じ再生位置で2本目は n コマ前のコマを表示する（2本目が n コマ後ろにずれる）
  - 「基準の瞬間に合わせる」と「コマ番号で合わせる」で効く。「進行率で合わせる」では隠し、ずらしは効かない
  - 再生の範囲・目盛りの位置・コマごとの値の表も、ずらした分を反映する。ずらした量は保存しない
- **まとめの表（打者のみ）**: コマごとの値の表の上に置く。行はまとめの3つ、列は「1本目・2本目・差」
- **読み方**: 打者では、座標の基準（胴の長さ・構えの腰）、開きが角度でないこと、奥行きを測れないこと、主審・捕手に乗り移ったときの見分け方を書く

### 14.7 画面の流れ

投手の流れ（§6）との違いだけを書く。

| # | 画面 | 打者モードでの違い |
|---|---|---|
| 0 | はじめに | 「打者のスイングを比べる」ボタンを足す。撮影の案内は「捕手の後ろから、構えから撮る。60fps 以上推奨」 |
| 6 | 打者の確認 | 一番大きく写った人を仮に選ぶ。背面からでは主審・捕手を選ぶことがあるので、「打者をタップ」と案内する |
| 7 | 瞬間の指定 | 「トップ」「インパクト」と右打ち／左打ち。投げ腕・打者の向きの切り替えは出さない |
| 9 | 書き出し | pose.json に打者の印を付ける（§14.8） |

「保存した解析結果で比べる」も、投手と打者を分ける。

### 14.8 保存ファイル（pose.json）

- `meta.subject` に `"pitcher"` または `"batter"` を書く。`SCHEMA_VERSION` は 1 のまま。Python 版は `meta` の余分な項目を読み飛ばすので、そのまま読める
- 読み込むとき、モードと `meta.subject` が違えば「投手の解析結果です」（逆は「打者の解析結果です」）と出して読み込まない
- `meta.subject` が無い古いファイルは、どちらのモードでも読める

### 14.9 失敗したときの案内

| 状況 | 扱い |
|---|---|
| 胴（肩と腰）がどのコマにも写っていない | 比べられない旨を出す（「打者の上半身と腰が写った動画で試してください」） |
| 途中のコマで打者を見失った | そのコマは値を空け、グラフは途切れる。補って作った値は出さない |
| 主審・捕手に乗り移った | 自動では見分けない。骨格の重ね描きで気づけるよう「読み方」に書き、打者を選び直してもらう |
| トップがインパクト以降 | 指定画面でその場で出す |

### 14.10 テスト

- 打者の計算は、合成した骨格データで確かめる（Python 版の元が無いので、数値一致の検証は無い）
  - 肩・腰を回転させたときの開きの値、時間差の符号
  - 左打者を左右反転しても右打者と同じ値になること
  - 頭（片耳が欠けたコマは空く）・両手の位置
  - 踏み込みの3区分の境目（±0.1）
  - トップ〜インパクトの進行率、まとめの値が出せないときの理由
- **投手側の回帰**: 既存の Python 版との一致テスト（`src/analysis/__fixtures__`）と比較画面のテストが、変更なしで通ることを必須にする
- 比較画面: ずらしたときの表示するコマ・範囲・目盛りの位置、「進行率で合わせる」で隠れること
- 保存ファイル: 打者の印の書き込みと読み込み、取り違えの拒否、印の無い古いファイルが読めること
- 画面: 開始画面のボタン、打者用の指定画面の文言、まとめの表
- 実際の動画での確認（手作業）: 捕手の後方から撮った手元の動画で、ユーザが確認する

### 14.11 未確認事項とリスク

- 背面から撮ったとき、姿勢推定の左右（左肩・右肩など）の取り違えがどれだけ起きるかは未確認。取り違えると開きの符号が一時的に反転する
- 主審・捕手への乗り移りの頻度は未確認。多ければ、追跡に胴の長さの急変の検出を足すことを検討する
- 「動画の先頭を構えとみなす」ので、構えの前から撮った動画では頭の移動・踏み込みの基準がずれる
